### 조사 (Dungeon Crawl Stone Soup)

DCSS는 층마다 **레이아웃 타입**을 달리한다:
`corridors`(1칸 좁은 길) · `rooms` · `passages`(넓은 다중칸 통로) · `narrowcaves` ·
`opencaves` · `city`(큰 공간 안에 건물) · `open` · `divisions`(붙어 있는 방들)

v1은 그중 **`rooms` 하나만** 썼다. 비슷한 크기의 사각형 방 + 직선 3칸 통로 + 균일한 기둥.
원조 Rogue가 방을 틱택토 격자로 배치했고 개발자들이 거기서 벗어나고 싶어 했다는데,
v1이 정확히 그 격자였다. **오너 지적이 맞다.**

- https://crawl.develz.org/wiki/doku.php?id=dcss:brainstorm:dungeon:layout_types
- https://howtomakeanrpg.com/r/a/rogue-dungeon-generation.html
- https://gravitymaker.github.io/posts/perfect-dungeon-1/

### 작업 — 한 층 안에서 구역마다 성격을 다르게

| 구역 | 타입 | 성격 |
|---|---|---|
| 서쪽 회랑 | colonnade | 좁고 긴 세로 공간 + 열주. 부속실이 겹쳐 L자 |
| 입구 광장 | open | 장애물이 거의 없다. 다른 구역과의 대비 |
| 서쪽 납골 | divisions | 좁은 통로로만 이어진 밀집 셀 |
| 북쪽 미로 | corridors | 좌우 번갈아 열리는 뱀 모양. 강제로 꺾인다 |
| 중앙 대청 | city | 큰 공간 안에 '건물'이 서 있고 그 사이가 길 |
| 남쪽 공동 | opencaves | 사각형을 겹쳐 불규칙한 윤곽 |
| 동쪽 | passages | 5칸 넓은 통로 위주, 방은 적다 |
| 최동단 | open | 거의 비어 있는 큰 홀. 마지막 대비 |

통로 폭도 1·2·3·5로 나누고 일부는 꺾이게 했다 — **직선 3칸 통일이 단조로움의 절반**이었다.
`layout_version` 1 → 2. 공간 25(방 17 + 포켓 8) · 통행 8759칸 · 긴 축 172타일.

### 근거

- **불규칙한 윤곽을 겹침으로 만들었다.** 남쪽 공동은 사각형 3개를 겹쳐 놓았다.
  로더가 이미 합집합으로 채우므로 새 기능 없이 비사각형 공간이 나온다.
- **`space_anchor_cell()`을 새로 만들었다.** `city`/`divisions` 구역은 방의 기하학적 중심이
  구조물 안에 들어간다. `StairResolver`가 중심을 계단 후보로 쓰고 있었기 때문에
  **7개 공간이 통째로 계단 후보에서 빠졌다.** 중심 대신 중심에서 나선형으로 넓혀
  처음 만나는 통행 가능한 칸을 대표 칸으로 쓴다. 순회 순서가 고정이라 결정적이다.
- **테스트도 중심 대신 대표 칸을 본다.** 원래 의도가 "공간에 도달 가능한가"이지
  "중심이 뚫려 있는가"가 아니었다. 불규칙 공간에서는 중심이 막힌 게 정상이다.

### 이동 E2E 테스트 — 측정 방식을 바로잡았다

30 tick 측정에서 정확히 `160/60 = 2.67px`가 모자랐다. **추측하지 않고 관측했다**:

1. 빈 SceneTree에서 같은 순서를 재현 → 15스텝 모두 `dx=5.3333`, 합계 정확히 80.0.
   `player.gd`도 `Movement`도 멀쩡하다.
2. 틱레이트 변경 직후 delta를 찍음 → 첫 프레임부터 `1/30`을 보고. "보고가 늦다"도 틀렸다.
3. 보고된 delta를 누적 → 누적 시간은 **15스텝**인데 이동은 **14.5스텝분**.

결론: **틱레이트 변경 직후 스텝이 이전 delta로 적분하면서 새 delta를 보고한다.**
런타임에 틱레이트를 바꾸는 건 이 테스트뿐이고 실제 게임에는 없는 상황이다.

→ 스텝 수를 가정하지 않고 보고된 delta를 누적해 논리 시간을 만들고,
전환 스텝을 흘려보낸 뒤 **정상 상태 속도**를 잰다. **허용치를 늘려 덮은 게 아니다.**

**변이 주입으로 검증했다** — `velocity *= delta`를 넣으니 속도가 5.3/2.7/1.3px/s로 무너지며
4단언 실패. 단위 `test_movement.gd`는 여전히 통과 — 이 파일의 존재 이유가 그대로 유효하다.
3회 반복 실행으로 안정성도 확인했다(이전에는 통과/실패를 오갔다).

최종: 단위 576단언 + 통합 20단언 전부 통과. 실행 확인 —

`half = width / 2` 뒤 `-half..half`. GDScript 정수 나눗셈이라 `width = 2` → `half = 1` →
`-1, 0, 1`의 **3칸**. 저작 데이터는 폭 1·2·3·5를 구분해 쓰는데
**저작한 지형과 실제 통행 지형이 달랐다.**

`lo = -(width / 2)`, `hi = lo + width - 1`로 바꿔 칸 수가 정확히 `width`가 되게 했다.
홀수는 중심 대칭, 짝수는 **음수 쪽(위/왼쪽)으로 치우친다** — 어느 쪽이든 골라야 하고
고정해두지 않으면 저작자가 예측할 수 없어서 표로 문서화했다.

**영향**: 통행 셀 8759 → **8630**. 정의 해시 `61c43cdb → 25f7a9c3`.
연결성·안티 스킵 테스트는 그대로 통과했다.

### P2-REV-005 — AI 뒤에 Validator가 없었다 ✅ (BLOCKER)

문서상 파이프라인에는 "AI ranking → Validator 재검증"이 있는데 실제로는
Hard Constraint를 **AI 호출 전에만** 적용하고, 신뢰하는 후보 배열을 **그대로** 넘기고 있었다.
GDScript의 배열·사전·객체는 참조라 어댑터가 `anchor`·`cost`를 직접 고칠 수 있다.

고친 것:
- `_ai_projection()` — 원시값만 담은 **사본**을 만든다. `WorldAnchor` 객체를 넘기지 않는다
- 반환값 검증 — 모르는 ID·비숫자·`NaN`·`INF` 거부, `MAX_AI_SCORE_DELTA`로 크기 제한
- **AI 이후 엔진이 원본 후보를 다시 Hard Constraint로 검증**

악성 어댑터 5종을 테스트에 넣었다: 후보 훼손 시도 · 모르는 ID · NaN/INF · 거대 점수 ·
사전이 아닌 반환값. **핵심은 "지금 AI가 없다"가 아니라 계약이 나중 AI에게
수정 가능한 신뢰 상태를 넘기지 않는 것**이다.

### P2-REV-006 — 물리 이동 후 되감기 ✅ (BLOCKER)

`move_and_slide()`로 **먼저 움직이고** 결과 좌표만 경계 안으로 되감고 있었다.
좌표는 돌아오지만 그 프레임에 몸체가 경계 밖에서 실제로 움직였고 충돌을 만들었다.

`AccessService.limit_motion()`을 만들어 **속도를 물리 이동 전에** 자른다. 축별로 잘라
경계를 따라 미끄러지는 이동은 살렸다. 사후 `clamp_move()`는 안전망으로 남겼다.

**여기서 예상 못 한 걸 하나 더 잡았다.** 처음엔 중심 셀만 봤는데 E2E가 실패했다 —
몸체(20×20)의 옆면이 경계를 넘어 밖의 `Area2D`에 닿았다. 중심이 안에 있어도 몸은 밖이었다.
`can_body_occupy()`로 **AABB가 덮는 모든 셀**을 보도록 고쳤다.
좌표 기반 단위 테스트로는 절대 잡을 수 없는 종류였다.

E2E는 경계 밖에 실제 `Area2D`를 놓고 **물리 접촉이 보고되는지**를 본다.
봉투가 없는 개체(NPC·야생동물)는 경계를 넘을 수 있는지도 함께 검사한다 (`FLR-023`).

### P3-T4/T5 — 함정 trigger mechanism (`FLR-028`)

`body is Player`를 쓰지 않는다. 함정은 "누가 밟았나"가 아니라 **"어떤 물리적 자극이 왔나"** 를 본다.

### P3-REV-001 [BLOCKER] — 반복형 함정의 단서가 사라졌다 ✅

`ClueView`가 `trap_has_fired`만 보고 흔적을 지웠다. 그런데 `FloorState.fire_trap()`은
`one_shot`이 아닌 함정의 `armed`를 **true로 유지**한다 — 함정 바닥처럼 반복해서 걸리는
치명 함정이 그렇다. 즉 **첫 발동 뒤 위험은 그대로인데 단서만 사라졌다.**
`TrapRuntime.should_fire()`는 그 함정을 실제로 다시 발동시킨다. `FLR-011` 위반이었다.

기준을 **"터졌는가" → "위험이 남아 있는가"(`armed`)** 로 바꿨다.

회귀 테스트는 요청대로 전체 흐름을 검사한다 —
반복형 발동 → 여전히 `armed` → 흔적 존재 → 재진입 시 재발동.
발사형은 반대로 발동 → 무장 해제 → 흔적 소멸을 함께 확인한다.
기존 `test_information_asymmetry`의 "fired면 위험 사라짐" 전제도 고쳤다.

**여기서 제 테스트의 결함을 하나 잡았다.** 처음 만든 헬퍼가 `ClueView`의 판단 조건을
**복제**하고 있어서, 변이를 넣어도 행동 단언은 통과하고 소스 가드만 잡혔다.
복제한 테스트는 구현이 바뀌어도 계속 통과하므로 아무것도 지키지 못한다.
판단을 `ClueView.shows_trace_for()`로 빼내 **그리기와 테스트가 같은 함수를 쓰게** 했다.
그러자 같은 변이를 행동 단언이 잡았다.

### P3-REV-002 [BLOCKER] — 지형 변경이 복원되지 않았다 ✅

### P3-REV-003 [HIGH] — 주소가 `cell`뿐이었다 ✅

`WorldAnchor`는 `world/region/cell/layer` 전체가 주소인데 `ground_items_at(cell)`은
좌표만 봤다. 1층은 region이 하나뿐이라 증상이 없지만, `FLR-023`상 층은 더 넓은 월드의
일부이고 2층 이후에는 같은 월드에 여러 region이 있다 — **옆 구역 바닥의 물건이 손에 잡힌다.**

`ground_items_here(WorldAnchor)` / `ground_items_in(region, layer)`로 바꾸고
`InteractionService`·`GroundItemView`도 region/layer를 구분하게 했다.
`put_ground_item()`은 다른 월드의 앵커를 **거부**한다 — 주소가 거짓말이 되므로.

### P3-REV-004 [HIGH] — 내구 등급이 소실됐다 ✅

### P3-REV-005 [BLOCKER] — 게임에서 벽 화살 함정이 아예 안 터졌다 ✅

`test_traps.gd`가 이걸 놓친 이유가 중요하다. 그 파일은 `from_thrown()`(= `IMPACT`)으로만
검사했다. **runtime은 멀쩡한데 게임이 잘못된 자극을 보내는 버그**라 순수 단위 테스트로는

**고친 방식**: 몸이 한 칸에 들어가면 **바닥을 누르고(`PRESSURE`) 동시에 그 공간의 것들을
스친다(`TOUCH`)**. `TrapStimulus.from_body_entering()`이 두 자극을 함께 만든다.

`PRESSURE`/`TOUCH`/`IMPACT`는 여전히 DESIGN이고 canon 문서는 건드리지 않았다.

**중복 발동 방지**: 한 번 들어갔는데 두 자극이 가면 둘 다 받는 함정이 두 번 터진다.
발사형은 두 번째가 무장 해제로 막히지만 **반복형은 막히지 않는다.**
`TrapRuntime.apply_all()`이 배치 안에서 이미 발동한 함정을 건너뛴다.

### 처리

**`TrapSensor` 어댑터 신설** — 월드 좌표계의 물리 사실(어디 있었고 어디로 갔나, 얼마나

- `sense_impact()` — 날아가던 물체가 멈춤 (충격 + 접촉)
- 개체별 마지막 칸을 들고 있어 서 있는 동안 반복 발동하지 않는다

**플레이어도 같은 어댑터를 쓰게 통합했다.** 경로가 갈라지면 `P3-REV-005`처럼
"한쪽 경로만 잘못된 자극을 보내는" 버그가 다시 난다.
`main`이 `TrapRuntime`이나 `TrapStimulus`를 직접 부르면 테스트가 실패한다.

**새 canon은 만들지 않았다.** 자극 종류는 그대로 3종이고 `FLR-028`이 정한

### 그 과정에서 테스트 인프라의 결함을 하나 잡았다

E2E를 어댑터 구조에 맞추다가 **단언 수가 13 → 10으로 줄었는데 PASS로 보고**되는 것을 봤다.
GDScript의 런타임 스크립트 에러는 **그 함수만** 중단시키고 `run()`은 계속 진행한다.
그래서 남은 단언이 조용히 사라져도 러너에는 정상으로 보인다.

두 겹으로 막았다:
- `TestCase.completed` — `run()`이 끝까지 갔는지. 최상위 중단을 잡는다
- 파일별 `MIN_ASSERTIONS` 하한 — 하위 함수에서 사라진 단언을 잡는다.
  단언을 **추가**할 때는 손댈 필요 없고 의도적으로 줄일 때만 낮춘다

주입 실험으로 확인했다 — `completed`만으로는 못 잡았고, 하한을 넣으니

## 2026-08-21 · P4-FIX-001 — 던진 돌이 함정을 터뜨리지 못했다

**담당**: 오너 (플레이 중 발견) · Claude (수정)

### 요청 (원문)
> 함정이 돌 던지기에 안터지는데

### 원인

`ThrownObject`가 **착지 지점에서만** `TrapSensor.sense_impact()`를 불렀다.

정작 그게 되지 않는 상태였다.

### 수정

비행 중 **새 칸에 들어갈 때마다** 자극을 낸다. 감지부를 건드렸으면 거기서 멈춘다 —
돌이 실선이나 압력판을 치고 계속 날아가지 않는다.
착지 시 중복 자극도 막았다(이미 그 칸에서 냈으면 다시 내지 않는다).

### ⚠ 기존 테스트가 왜 못 잡았는가 — 이게 더 중요하다

- `test_nonplayer_stimulus_e2e.gd`는 `sense_impact()`를 **함정 칸에서 직접** 불렀다
- `test_combat_e2e.gd`는 투사체가 **생겼다 사라지는지**만 봤다

`P3-REV-005`("runtime은 옳은데 게임이 잘못된 자극을 보낸다")와 같은 계열이다 —
**부품은 맞고 호출 지점이 틀린 버그.** 부품을 각각 검사하는 테스트로는 구조적으로 못 잡는다.

교훈: **"A가 B를 호출한다"를 검사하는 것으로는 부족하고, "실제 상황에서 A가 B에게
올바른 값을 준다"를 봐야 한다.** 이번엔 "3칸 앞에서 던진다"는 거리가 그 값이었다.
