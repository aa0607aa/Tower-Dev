## 1. 오너 제안 (원안)

> 데이터 마이닝은 피할 수 없는 숙명이다. 마이닝 자체를 막는 것이 아니라, 일반적인 방법으로는
> 다 확인할 수 없을 만큼 수많은 데이터를 쌓고 더미 데이터를 섞어서 원하는 내용을 찾지 못하게 만든다.

## 2. 검토 결과 요약

**전제는 옳다. 그리고 「탑」의 기존 아키텍처와 매우 잘 맞는다.**
"마이닝을 막을 수 있다"는 환상을 버리고 설계로 방어한다는 방향은 이 프로젝트에 이미 깔려 있는
사고방식(`SYS-005` 정보 비대칭)의 파일 레벨 확장이다.

**그런데 "볼륨 + 더미 데이터"를 문자 그대로 구현하면 실패한다.** 이유는 아래 §3.
실패하는 이유를 알면 성공하는 형태가 보이고, 그 형태는 「탑」에서 **거의 공짜**다(§4).

## 3. 왜 "볼륨 + 더미"만으로는 실패하는가

### 3.1 마이닝은 사람이 눈으로 하지 않는다

핵심 오해가 여기 있다. "너무 많아서 사람이 다 못 본다"는 방어는 **사람이 본다는 가정** 위에 서 있다.
실제 데이터 마이너는 파일을 덤프해서 스크립트로 처리한다. 행이 500개에서 50,000개로 늘어나는 것은
그들에게 **몇 분의 차이**지 몇 달의 차이가 아니다. 그리고 한 사람이 만든 파서는 커뮤니티 전체가
공유한다. 볼륨은 **1인분의 노력을 늘리는 게 아니라 전체 커뮤니티에서 1회분만 늘린다.**

### 3.2 코드가 참조하지 않는 데이터는 즉시 걸러진다

이게 결정적이다. 더미 데이터를 넣으면 마이너는 이렇게 한다.

```
1. 데이터 테이블 전체를 덤프한다
2. 코드/스크립트에서 실제로 참조되는 ID 집합을 추출한다
3. 교집합만 남긴다  ← 더미가 여기서 전부 사라진다
```

한 번도 스폰되지 않고, 어떤 테이블에서도 참조되지 않고, 어떤 코드 경로로도 도달할 수 없는 항목은
**"진짜가 아님"이라는 라벨을 스스로 달고 있는 것과 같다.** 오히려 진짜 목록을 더 선명하게 만들어준다.

### 3.3 더미는 생김새로 들킨다

실전에서 더미 데이터가 걸러지는 가장 흔한 경로다.

| 들키는 지점 | 왜 |
| --- | --- |
| 이름이 `trap_dummy_042`, `item_test_7` | 말할 것도 없다 |
| ID가 끝에 연속으로 몰려 있음 | 진짜 데이터는 개발 과정에서 흩어져 생긴다 |
| 필드가 비어 있거나 기본값 | 진짜는 손으로 채워져 값이 제각각이다 |
| 스프라이트·현지화 텍스트가 없음 | 에셋 참조가 비면 그 자체가 표식 |
| **검증 규칙을 만족하지 않음** | §5 — 가장 위험한 함정 |

## 4. 실제로 작동하는 형태 — 「탑」에는 이미 절반이 있다

작동하는 방어는 "많이 쌓기"가 아니라 **"배포 파일에 답을 넣지 않기"**다.

> **정답을 배포하지 말고, 정답을 만드는 규칙을 배포하라.**

「탑」은 이미 이 구조다. `SYS-003`이 "모든 랜덤은 시드 또는 결과를 저장한다"고 요구하는데,
이 말은 **생성 결과가 배포 파일이 아니라 플레이어의 세이브에 산다**는 뜻이다.

그래서 마이너가 배포 파일에서 얻을 수 있는 것은 **가능성 공간**이고,
얻을 수 없는 것은 **이번 판의 답**이다.

| 마이너가 알 수 있는 것 | 알 수 없는 것 |
| --- | --- |
| 열매 효과가 24종 존재한다 | **이 월드에서** 붉은 열매가 무엇인가 (`WLD-008`) |
| 함정 타입 목록과 단서 종류 | **이번 판** 1층 어디에 무엇이 있는가 (`FLR-002`) |
| 유배자 아키타입 풀 | 지금 3층에 있는 고참이 누구인가 |
| 스킬 후보 발생 규칙 | 이 회차의 유니크 스킬 소유자 (`SKL-004`) |
| 인과 그래프의 노드 종류 | 이 월드의 역사가 어떻게 갈렸는가 (`WLD-009`) |

로그라이크에서 비밀의 대부분은 오른쪽 열에 있다. 그리고 오른쪽 열은 **원리적으로 마이닝 불가능**하다.
파일에 없기 때문이다. 이건 난독화가 아니라 구조다.

**따라서 진짜 결론: 「탑」은 볼륨 없이도 이미 상당히 강하다.**

## 5. 가장 위험한 함정 — 검증 규칙이 곧 지문이 된다

이 항목만은 반드시 짚고 넘어가야 한다. 더미 데이터 전략이 실전에서 무너지는 지점이 여기다.

**우리가 진짜 데이터에만 적용하는 규칙은 전부 "진짜 판별기"가 된다.**

구체적인 예가 이미 이 프로젝트에 있다. `FLR-011`은 **치명 함정의 `clues[]`가 비면 테스트 실패**로
강제한다. 그런데 더미 함정을 대량으로 넣으면서 단서 작성을 생략하면?

```
clues[] 가 비어 있다  →  더미다
clues[] 가 채워져 있다 →  진짜다
```

**한 줄짜리 필터로 전멸한다.** 볼륨을 아무리 키워도 소용없다.
같은 논리가 스프라이트 유무, 현지화 유무, 밸런스 수치의 자연스러움에 전부 적용된다.

여기서 진짜 비용이 나온다:

> **더미 데이터는 진짜 데이터가 만족하는 모든 불변식을 똑같이 만족해야 한다.
> 즉 더미를 만드는 비용은 진짜를 만드는 비용과 거의 같다.**

"대충 채워 넣는 가짜"는 존재할 수 없다. 존재하는 순간 지문이 된다.
그래서 대부분의 게임이 이 전략을 시도했다가 실패한다.

## 6. `FLR-001`과의 직접 충돌 — 1층 지형은 은닉할 수 없다

**canon 차원의 결과이므로 오너 확인이 필요하다.**

`FLR-001`(1층 지형은 고정)은 1층 맵이 **배포 파일에 그대로 들어간다**는 뜻이다.
따라서 **1층 지형은 원리적으로 숨길 수 없다.** 더미 맵을 아무리 섞어도, 실제로 로드되는 것은
하나뿐이므로 코드 참조 한 번이면 어느 것이 진짜인지 드러난다.

1층에서 숨길 수 있는 것과 없는 것:

| 숨길 수 있다 (시드 기반, `FLR-002`) | 숨길 수 없다 (고정, `FLR-001`) |
| --- | --- |
| 어느 파밍 지점에 무엇이 있는가 | 방·통로·막다른 길의 배치 |
| 어떤 유배자가 어디 스폰되는가 | 함정 **슬롯**의 위치 |
| 함정이 활성인지 여부, 어떤 종류인지 | 계단이 놓일 수 있는 후보 지점 |

**즉 1층 튜토리얼의 설계는 "맵이 공개된 상태"를 전제로 해야 한다.**
이게 문제인지 아닌지는 설계 의도의 문제이고, 내가 판단할 사안이 아니다.
개인적으로는 문제가 아니라고 본다 — 1층은 튜토리얼이고, `FLR-011`에 따라 어차피 모든 치명 함정에
단서가 있어야 하므로 애초에 "몰라서 죽는" 층이 아니다. 하지만 **오너가 확인해야 한다.**

| 비용 | 내용 |
| --- | --- |
| 저작 비용 | §5 때문에 더미도 진짜만큼 손이 간다 |
| 디버깅 | 로그·세이브·밸런스 도구에서 노이즈가 늘어난다 |
| 결정성 테스트 | `SYS-003`/G-4 검증 대상이 늘어나 느려진다 |
| 저장소 | 데이터·에셋 용량 증가 |
| **우리 도구도 못 거른다** | 아래 |

마지막 항목이 특히 중요하다. **`is_dummy` 플래그를 넣으면 안 되고, 더미를 별도 파일·폴더에 모아도
안 된다.** 둘 다 §3.2의 필터를 그대로 통과시켜 전략을 즉시 무효화한다.
그런데 그 말은 **우리 자신의 밸런스 도구와 디버거도 더미를 구분할 수 없다**는 뜻이다.
개발 전용 빌드 플래그나, 배포에 절대 포함되지 않는 외부 매니페스트가 따로 필요해진다.

## 8. 제안 — 3단계로 나눠서 채택

전부 하거나 안 하거나가 아니라, **비용 대비 효과 순서**로 층을 나눈다.

### Tier 1 — 지금 채택 (추가 비용 0)

이미 하고 있거나 하기로 한 것을 **명시적 정책으로 승격**한다.

- 정답을 배포하지 않고 생성기를 배포한다 (`SYS-003`)
- 월드·회차 단위 귀속을 유지한다 (`WLD-008`, `SKL-004`)
- 미발견 정보를 UI·AI 컨텍스트에 넣지 않는다 (`SYS-005`)
- **파일에 "정답 테이블"을 만들지 않는다** — 예: `열매 → 효과` 매핑을 배포 데이터로 두지 않는다

### Tier 2 — 지금 채택 (규율 비용만)

- **`is_dummy` 같은 플래그를 절대 만들지 않는다.** 어떤 이름으로도.
- **더미 전용 파일·폴더·ID 대역을 만들지 않는다.**
- 모든 데이터는 종류에 관계없이 **동일한 검증 규칙을 통과해야 한다.** (`FLR-011` 포함)
- 개발용 구분이 필요하면 **배포에 포함되지 않는 외부 매니페스트**로만 관리한다

Tier 2는 코드를 늘리지 않지만, **나중에 Tier 3를 하기로 결정했을 때 그것이 가능한 상태**를 지금
확보해 둔다. 나중에 되돌리기 가장 비싼 부분이 바로 이것이다.

### Tier 3 — 보류, 백로그 (비쌈)

- 실제 볼륨 확보와 "살아 있는 더미" 투입

**지금 하지 말 것을 권한다.** 이유:

1. 진짜 콘텐츠가 아직 없다. 진짜가 없는데 가짜를 만들 수 없다.
2. §5 때문에 더미는 진짜만큼 비싸다. MVP 전에 쓸 예산이 아니다.
3. 유일하게 유효한 더미는 **"실제로 낮은 확률로 등장하는 진짜 콘텐츠"**다.
   그건 더미가 아니라 그냥 콘텐츠이고, 콘텐츠 제작 단계의 일이다.

**Tier 3의 올바른 형태**: 등장하지 않는 가짜를 넣는 게 아니라, **모든 항목이 실제로 등장 가능하게**
만들고 등장 확률만 다르게 준다. 그러면 §3.2의 "코드 참조" 필터가 무력화된다 — 전부 참조되기 때문이다.
이게 유일하게 지속 가능한 형태이고, 동시에 **가장 비싼** 형태다.

## 10. 요약

- 전제("마이닝은 막을 수 없다, 설계로 방어한다")는 **옳고, 채택을 권한다.**
- 그러나 **볼륨과 더미만으로는 막지 못한다.** 자동화된 마이너에게 볼륨은 몇 분이고,
  참조되지 않는 더미는 한 번의 필터로 사라진다.
- **작동하는 방어는 "정답을 배포하지 않는 것"**이고, 「탑」은 시드 기반 구조 덕에 이미 절반쯤
  그렇게 되어 있다. 이걸 명시적 정책으로 올리는 것이 가장 남는 장사다.
- 더미를 하려면 **진짜와 동일한 불변식을 만족해야** 한다. 그래서 비싸다. 콘텐츠가 생긴 뒤에 한다.
- 지금 반드시 지킬 것은 하나다 — **`is_dummy` 플래그와 더미 전용 폴더를 만들지 않는 것.**
  이건 공짜이고, 나중에 되돌리기 가장 비싸다.
