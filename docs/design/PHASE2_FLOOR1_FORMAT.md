## 3. 쟁점 A — 지형을 무엇으로 표현하는가

### 선택지

| | A. TileMapLayer 씬(`.tscn`) | B. 텍스트 그리드(`.txt`) | C. JSON 좌표 목록 |
| --- | --- | --- | --- |
| 맵 제작 | **에디터로 그림** (쉬움) | 손으로 문자 편집 | 손으로 좌표 입력 (최악) |
| diff 가독성 | 나쁨 (`.tscn` 바이너리성 배열) | **좋음** (한 줄이 한 행) | 보통 |
| 테스트 파싱 | 씬 로드 필요 (headless 가능) | **문자열만 읽으면 됨** | 쉬움 |
| 충돌·렌더 | **엔진이 자동 처리** | 로더가 생성해야 함 | 로더가 생성해야 함 |
| `SYS-004` 시각/데이터 분리 | 주의 필요 | **명확히 분리** | 명확히 분리 |

### 구현 담당 권고 — **A(TileMapLayer)를 편집·SSOT로, 로더가 `FloorState`를 만든다**

처음엔 B(텍스트)를 권하려 했으나 뒤집었다. 이유:

1. **맵을 그리는 것은 오너의 작업이다.** 1층은 고정 지형이라 **한 번 잘 그리는 것이 곧 게임의 질**이고,
   `FLR-015`(지형 암기가 영구 성장)·`CHR-014`(지식 기반 메타 성장) 때문에 레이아웃의 완성도가
   다른 층보다 훨씬 중요하다. 문자로 그리게 하면 그 작업이 고통스러워지고 결과가 나빠진다.
2. **충돌·렌더를 엔진이 처리한다.** B/C는 로더가 `StaticBody2D`와 콜리전을 만들어야 하고,
   그건 우리가 유지해야 할 코드가 늘어난다는 뜻이다.
3. **테스트 파싱이 실제로 문제가 안 된다.** headless에서 `.tscn`을 로드해
   `TileMapLayer.get_used_cells()`로 셀을 읽을 수 있다. 2-1/2-2 검증에 충분하다.
4. `SYS-004`는 **런타임에 `FloorState`라는 별도 데이터 객체를 만들면** 지켜진다.
   씬은 저작 포맷이고 게임 로직은 `FloorState`만 본다. 노드가 상태를 소유하지 않는다.

**단점을 인정한다**: `.tscn` diff는 읽기 어렵다. 맵이 바뀌었을 때 "무엇이 바뀌었는지" 리뷰가 힘들다.
→ 완화책: 로더가 만든 `FloorState`의 **지형 해시**를 테스트가 출력하게 하고, 해시가 바뀌면
   맵이 바뀐 것이므로 커밋 메시지에 의도를 적게 강제한다.

### GPT에게 묻고 싶은 것

- 지형 저작을 에디터로 하는 대신 diff 가독성을 잃는 교환이 타당한가?
- `.tscn`을 SSOT로 두면 나중에 **2층 이후 프로시저럴 생성기(`B-002`)** 와 포맷이 갈라진다.
  생성기는 데이터를 만들지 씬을 만들지 않는다. 지금부터 중간 표현(`FloorState`)을 SSOT로 두고
  1층은 "씬 → FloorState 변환기"를 쓰는 게 나은가?

## 4. 쟁점 B — 고정과 동적의 경계 (`SYS-009` Tier 1의 핵심)

**이게 이 설계안에서 가장 중요한 부분이다.** 여기를 잘못 그으면 `SYS-009`가 포맷 수준에서 깨진다.

### 제안하는 경계

| 배포 파일에 **있음** (고정, `FLR-001`) | 세이브에만 **있음** (시드, `FLR-002`) |
| --- | --- |
| 벽·바닥 타일, 방 ID, 통로 | — |
| 시작점 | — |
| **함정 슬롯의 좌표와 모양** | **그 슬롯에 실제로 무엇이 들어가는가 (타입·활성 여부)** |
| **파밍 지점의 좌표** | **그 지점에 무엇이 놓이는가** |
| 계단 후보 지점 (쟁점 C) | 파티별 실제 계단 |
| 유배자 스폰 후보 지점 | 누가·몇 명 스폰되는가 |

### 왜 이렇게 긋는가

`SYS-014`가 이미 **1층 지형은 은닉 불가**라고 확정했다. 즉 방·통로·슬롯 위치가 공개되는 것은
canon이 받아들인 결과다. 그런데 여기서 한 발 더 나가 **슬롯 파일에 `trap_type: pitfall`을 적어버리면**
`SYS-009` Tier 1("정답 테이블을 배포 파일에 두지 않는다")이 깨진다.

> 슬롯은 "여기에 함정이 있을 수 있다"까지만 말한다.
> "그게 낙하 함정이다"는 세이브에만 있다.

이 구분을 **포맷이 강제해야 한다.** 사람이 조심하는 것에 맡기면 언젠가 깨진다.
→ 검증 테스트: 배포 데이터 파일에 함정 **타입** 필드가 존재하면 **테스트 실패**.

### 주의 — `FLR-011`과의 충돌 가능성

`FLR-011`은 치명 함정에 **사전 단서가 필수**라고 한다. 단서가 슬롯(고정)에 붙으면
단서만 보고 함정 타입을 역산할 수 있다. 단서도 **인스턴스(시드) 쪽**에 있어야 한다.
즉 "이 슬롯의 단서는 무엇인가"도 배포 데이터에 없어야 한다.

이건 `SYS-009` Tier 2의 "진짜에만 적용되는 검증 규칙이 판별기가 된다"와 같은 함정이다.

## 5. 쟁점 C — 계단 (`FAC-001` · `FAC-002`)

설정서 §6.1: *"계단은 지형 자체가 아니라 파티 귀속 특수 시설로 취급한다.
1층 맵은 고정이지만 계단은 파티별 귀속 규칙에 따라 **같은 고정 맵 안에서 별도 상태로 존재**한다."*

여기서 확실한 것과 불확실한 것이 갈린다.

**확실**: 계단은 고정 지형이 아니다. 파티마다 다르다. `party_stairs[]` 배열이다.

**불확실 — 오너 결정이 필요하다**:
1. 계단이 놓일 수 있는 **후보 지점이 고정 데이터로 정의**되는가,
   아니면 **바닥이면 어디든** 가능한가?
   - 후보 고정 → `SYS-014` 표의 "계단이 놓일 수 있는 후보 지점"과 일치. 마이닝으로 후보 목록이 공개됨
   - 어디든 → 마이닝으로 알 수 있는 게 없음. 대신 "말도 안 되는 위치"가 나올 수 있어 제약이 필요
2. 계단 위치는 **파티 결성 시** 정해지는가, **층 진입 시**인가?
   - `FAC-005`("새 파티를 결성하면 파티장의 계단으로 귀속")를 보면 파티 단위 사건에 묶이는 듯하나
     최초 1인 파티의 계단이 언제 생기는지는 원문에 없다

**임의로 정하지 않는다.** MVP는 파티 1개 기준으로 단순화하되(`FAC-002`) 스키마는 배열을 전제한다.

## 6. 쟁점 D — 결정성을 어떻게 보장하는가 (`SYS-003`)

`SYS-003`은 "시드 **또는** 생성 결과를 저장"이라고 한다. 둘 중 무엇을 고를까.

| | 시드만 저장 → 재생성 | **생성 결과를 저장** |
| --- | --- | --- |
| 세이브 크기 | 작음 | 큼 (1층 규모면 무시 가능) |
| 배치 로직 변경 시 | **기존 세이브가 조용히 달라진다** | 안전 |
| 검증 | 로직이 결정적인지 계속 증명해야 함 | 저장된 것과 비교하면 끝 |

### 권고 — **생성 결과를 저장한다**

`SYS-003`의 핵심 문장은 "플레이어가 보지 않았다고 해서 다시 생성되지 않는다"이다.
시드 재생성 방식은 **배치 로직을 한 줄 고치는 순간 과거 세이브의 세계가 바뀐다.**
그건 이 canon을 조용히 위반하는 것이고, 위반했다는 사실조차 드러나지 않는다.

시드는 **재현·디버깅용으로 함께 저장**하되, 진실은 저장된 결과다.

## 7. 제안하는 데이터 구조 (초안)

```
data/floors/floor1_fixed/
  floor1.tscn          # 지형 저작 SSOT — TileMapLayer (벽/바닥)
  floor1_meta.tres     # 좌표 기반 고정 데이터 (아래)
```

`floor1_meta` (고정 — 배포됨):

```
floor_id: "floor1"
theme_id: "ancient_temple"        # FLR-013
map_bounds: Rect2i                # FLR-017
start_points: Array[Vector2i]     # 시작점 후보
rooms: Array[{ id, rect, tags }]  # 방 식별 (연결성 검사·서든데스 붕괴 순서용)
trap_slots: Array[{ id, cell, shape }]        # 좌표와 모양만. 타입 없음 (§4)
loot_points: Array[{ id, cell, tier_hint? }]  # tier_hint는 쟁점 — §8 Q4
spawn_points: Array[{ id, cell, kind }]       # kind = exile / none
stair_candidates: Array[Vector2i]             # 쟁점 C에 따라 존재 여부가 갈림
```

`FloorState` (런타임·세이브 — 결과 저장):

```
floor_id / theme_id / map_source: FIXED
generation_seed                   # 재현용. 진실은 아래 실체화된 결과다
map_bounds / room_ids[]
party_stairs: Array[{ party_id, cell, discovered_by[] }]   # FAC-002
traps: Array[{ slot_id, type, clues[], armed, one_shot, fired }]  # FLR-011/012
loot: Array[{ point_id, item_id, quality, state }]
npcs: Array[{ npc_id, spawn_point_id, ... }]
discovered_cells[] / collapsed_cells[]
elapsed_seconds / sudden_death_state
event_flags{}
```

**핵심**: `trap_slots`(고정)에는 `type`도 `clues`도 없고, `traps`(세이브)에만 있다.

T7을 마지막이 아니라 **T1과 함께** 넣는 것도 방법이다 — 포맷이 굳기 전에 가드를 세우는 쪽이 싸다.

## 10. 이 설계안의 한계

- **1층의 실제 크기·방 개수를 모른다.** 설정서에 없다. 맵 저작 전에 오너와 정해야 한다.
- 서든데스 붕괴(`FLR-005`, 가장자리부터)가 방 단위인지 셀 단위인지 정하지 않았다. PHASE 5 사안이지만
  `rooms`/`map_bounds` 설계에 영향을 줄 수 있어 미리 물어볼 가치가 있다.
- 파티 시스템이 아직 없다. `party_stairs[]`는 스키마만 잡고 MVP는 파티 1개로 간다 (`FAC-002`).

## 11. GPT 설계 검토 — 2026-08-18

> **판정: 방향은 좋지만 D-016을 현재 형태 그대로 Resolved 하면 안 된다.**
> 구현 착수 전에 아래 Canon 정합성 2건과 데이터 구조 보정안을 먼저 처리한다.

### 11.1 [CANON CONFLICT] 함정 타입은 고정인가, 시드로 바뀌는가

```text
[CANON CONFLICT]
위치: 설정서 v1.1 §6.1 / DECISIONS D-003 / FLR-002 ↔ SYS-014 / D-016 §4·§7
현재 Canon(A): 1층에서 랜덤한 것은 전리품·유배자·상태/활성 플래그다.
               설정서 §6.1은 "함정 구조"와 위험지점을 고정 지형 학습 대상으로 둔다.
이번 구현안/색인(B): 함정 슬롯 위치만 고정하고, 슬롯의 실제 함정 타입은 시드 결과로 두며 세이브에 저장한다.
충돌 내용: B의 "함정 타입 랜덤"은 설정서/D-003/FLR-002의 랜덤 목록에 포함되지 않는다.
           SYS-014는 데이터마이닝 정책 정리 과정에서 "함정 활성 여부·종류"를 숨길 수 있다고 적어
           원문보다 랜덤 범위를 넓힌 상태다.
필요한 결정: A 유지(함정 타입/구조 고정, 활성·소모 상태만 동적) /
             B로 변경(슬롯 고정 + 타입은 시드 랜덤으로 오너가 명시 확정) / 제3안
영향 범위: D-003 · FLR-001/002 · FLR-011 · SYS-014 · D-016 §4/§7 · PHASE 2~3
```

**GPT 권고는 A 유지.** 1층은 지형·위험지점을 외우는 메타 성장의 비중이 큰 층이고,
함정 타입까지 고정하면 설정서 §6.1의 "함정 구조"와 가장 직접적으로 맞는다.
타입을 매 판 바꾸고 싶다면 가능하지만, 그때는 데이터 마이닝 때문에 몰래 구현하지 말고
**오너가 D-016에서 설정서보다 넓은 랜덤 범위를 명시적으로 승인**해야 한다.

이 결정에 따라 `clues[]`의 위치도 달라진다.

- A(타입 고정): 타입별 사전 단서도 고정 정의에 둘 수 있다. 실제 `armed/fired` 등 상태만 세이브.
- B(타입 랜덤): 단서는 선택된 타입과 함께 인스턴스화되어야 하며 세이브 결과에 들어간다.

따라서 현재 문서의 **"단서는 반드시 세이브 쪽이어야 한다"는 결론도 Q0 결정 전에는 확정하면 안 된다.**

### 11.2 [CANON CONFLICT] 계단 후보 지점은 이미 고정 Canon인가, 아직 미정인가

```text
[CANON CONFLICT]
위치: SYS-014 ↔ 설정서 v1.1 §6.1 · FAC-001/002 · D-016 §5 Q2
현재 Canon(A): SYS-014 표는 "계단이 놓일 수 있는 후보 지점"을 고정·마이닝 가능 영역으로 적고 있다.
이번 구현안/원문(B): 설정서는 계단이 고정 맵 안의 파티 귀속 별도 상태라고만 정하며,
                   정확한 후보 지점 목록의 존재는 직접 정하지 않는다. D-016도 Q2를 미정으로 올렸다.
충돌 내용: 색인은 후보 지점 고정을 이미 CANON으로 보지만, 원문/오너 D-012 Q3의 직접 승인 문구는
           "1층 지형 은닉 불가 전제에 동의"였고 후보 지점 방식까지 명시 확정했는지는 불분명하다.
필요한 결정: A 재확인(고정 후보 지점 채택) / B로 정정(바닥+제약으로 동적 선택) / 제3안
영향 범위: SYS-014 · FAC-001/002 · D-016 Q2 · TEST_CHECKLIST 2-2 · PHASE 2
```

**GPT 권고는 고정 후보 지점.** 이유는 마이닝 방어가 아니라 레벨 디자인 때문이다.
고정 후보를 저작하면 막다른 길·파밍 동선·붕괴 탈출 압박을 고려해 계단이 나올 수 있는 장소를
사람이 통제할 수 있다. "바닥이면 어디든"은 결국 코드에 배치 제약을 많이 넣게 되어
후보 목록을 데이터가 아니라 알고리즘으로 숨기는 것에 가까워진다.

단, 이 권고를 채택하려면 오너가 Q2에서 다시 확정하고 SYS-014의 출처 의미를 명확히 한다.

### 11.3 Q1 지형 포맷 — **A를 채택하되 `FloorDefinition` 중간 표현을 둔다**

TileMapLayer 저작은 타당하다. 하지만 **`FloorState`를 정적 지형의 SSOT로 만들지는 않는 것을 권고**한다.
`FloorState`는 이름 그대로 플레이 중 변하는 상태여야 한다.

권장 구조:

```text
[1층 저작]
TileMapLayer scene + floor1_meta.tres
          ↓ loader
FloorDefinition (불변 · 런타임 공통 표현)
          ↓ instantiate/realize
FloorState (가변 · 세이브되는 결과)

[2층+]
Procedural Generator
          ↓
FloorDefinition (같은 인터페이스)
          ↓
FloorState
```

- **저작 SSOT**: 1층의 `TileMapLayer scene + floor1_meta.tres`. 같은 사실을 두 파일에 중복하지 않는다.
- **공통 런타임 표현**: `FloorDefinition`. 고정/생성 층 모두 같은 소비 인터페이스를 사용한다.
- **가변 상태**: `FloorState`. 전리품 실체화 결과, 계단 귀속, 함정 상태, 발견/붕괴/시간 등을 보유한다.
- `FloorDefinition`을 별도 커밋 파일로 또 저장해 **두 번째 정본**을 만들지는 않는다. 로드/생성 시 만든다.

따라서 Q1에 대한 GPT 답은 **A + 런타임 IR(`FloorDefinition`)**이다.
원래 Q1의 C처럼 변환 산출물을 별도의 영구 SSOT로 두자는 뜻은 아니다.

`.tscn` diff 가독성 문제는 지형 해시만으로는 "바뀌었다"까지만 알 수 있다.
필요하면 테스트/도구가 **비정본 human-readable map audit dump**를 생성하게 한다.
그 덤프는 검수 편의물이며 게임이 읽는 두 번째 데이터 원본으로 만들지 않는다.

### 11.4 Q3 계단 생성 시점 — A/B 이분법보다 수명주기를 명시하는 C안 권고

`FAC-005`는 새 파티 결성 시 **파티장의 기존 계단으로 귀속**된다고 정한다.
따라서 "파티가 결성될 때마다 새 계단 생성"은 원문과 잘 맞지 않는다.

GPT 권고 C안:

1. 층에 처음 진입할 때 현재 솔로/파티 소유권에 대한 계단 상태를 resolve/create한다.
2. 기존 계단을 가진 파티장에게 합류하면 **새 계단을 생성하지 않고** 파티장의 계단 이용권으로 전환한다 (`FAC-005`).
3. 탈퇴 후 기존 계단 유지/신규 생성은 `FAC-006/007` 규칙으로 처리한다. 정확한 확률·조건은 TBD를 유지한다.

최초 솔로 계단의 정확한 생성 시점은 설정서가 직접 명시하지 않으므로 **오너 승인은 필요**하다.

### 11.5 Q4 · Q5 권고

- **Q4 `tier_hint`**: **두지 않는다.** 현재 Canon은 파밍 지점과 내용물 랜덤까지만 정한다.
  특정 고정 지점에 "좋은 전리품 확률이 높음"을 붙이는 것은 새 밸런스 규칙이고 마이닝 가능한
  확률 정보가 된다. 이후 레벨 디자인이 필요로 할 때 별도 DESIGN으로 추가한다.
- **Q5 결정성**: **생성 결과 저장**을 채택한다. seed도 재현/디버그용으로 함께 보존한다.
  추가로 `floor_definition_version/hash` 또는 이에 준하는 식별자를 세이브에 기록해
  고정 맵 정의가 패치로 바뀌었을 때 기존 세이브가 조용히 다른 좌표 체계에 얹히지 않게 한다.

### 11.6 스키마에서 구현 전에 보정할 것

1. **`start_points: Array`의 의미를 확정한다.** 설정서/D-003은 플레이어 시작 위치 랜덤을 정하지 않았다.
   MVP에서 랜덤 선택할 근거가 없다면 `start_cell` 단일 값으로 시작한다.
   복수 시작점을 원하면 그 선택 규칙을 D-016에 명시한다.
2. **`map_bounds: Rect2i`를 실제 이동 가능 경계의 유일한 표현으로 삼지 않는다.**
   고정 사원 지형이 비정형이면 직사각형은 실제 walkable 영역을 표현하지 못한다.
   TileMapLayer의 walkable/collision 셀 집합을 정본으로 하고 Rect2i는 broad bounds로만 쓴다.
3. **`rooms: {rect}`도 지형을 중복 정의하지 않는다.** 방/영역 의미가 필요하면
   geometry 자체가 아니라 semantic area ID + 셀 집합/영역 참조로 두거나 실제 타일에서 파생한다.
4. **`trap_slots.shape`가 함정 타입을 암시하지 않게 한다.** Q0에서 타입 랜덤을 선택한다면
   `shape`는 generic footprint/배치 제약만 의미해야 한다. 타입별 trigger shape는 인스턴스 쪽이다.
5. **포맷 가드 테스트(T7)는 마지막이 아니라 T1과 동시에 만든다.** 스키마를 만든 직후부터
   금지 필드/고정성/정적·동적 경계를 실패시키는 편이 싸다.
6. **2-2 경로 테스트는 두 층으로 나눈다.** 고정 후보제를 택한다면 모든 허용 시작점→모든 계단 후보의
   정적 도달성을 먼저 전수 검사하고, 그 다음 seed sweep으로 "생성기가 유효 후보만 고른다"를 확인한다.
   seed 100~1000회만으로 지형 연결성 자체를 증명하려 하지 않는다.

### 11.7 데이터 마이닝 정책 validator의 범위

현재 제안의 "배포 데이터 파일에 함정 `type` 필드가 있으면 실패"는 **범위를 좁혀야 한다.**
`DATAMINING_POLICY.md`는 마이너가 **함정 타입 목록과 단서 종류 자체는 알 수 있다**고 명시한다.
숨기는 것은 "이번 판 어느 슬롯에 어떤 타입이 실체화됐는가"라는 **정답 매핑**이다.

따라서 Q0에서 타입 랜덤(B)을 택한다면 검증 대상은:

- `data/floors/floor1_fixed/`의 **slot → trap_type / clue 매핑 금지**
- 일반 `data/traps/`의 trap type 정의·clue template까지 금지하지 않음

Q0에서 타입 고정(A)을 택한다면 그 매핑 자체가 공개 가능한 고정 설계가 되므로
`SYS-014`/`SYS-009`의 표현을 함께 정정해야 한다.

### 11.8 티켓 순서 수정 제안

오너 결정 후 구현 담당 타당성 확인을 거쳐 다음처럼 잡는 것을 권고한다.

```text
T0  D-016 Q0~Q5 확정 + Canon 색인 정합화
T1  FloorDefinition / FloorState 경계 + floor1_meta 스키마 + 포맷 가드 테스트
T2  TileMapLayer greybox 저작본 + 로더 → FloorDefinition
T3  고정 지형/후보 전수 연결성 검증
T4  동적 결과 실체화 + deterministic RNG
T5  결과 저장/로드 + definition version/hash 검증
T6  party_stairs[] 수명주기
T7  오너 greybox 플레이테스트 후 맵 규모/방 구성 조정
```

실제 아트 완성은 PHASE 8이므로 PHASE 2의 T2/T7은 **회색박스 레벨 디자인**으로 충분하다.
1층 크기·방 개수는 Canon이 아니라 DESIGN이므로 한 번에 숫자를 영구 고정하기보다
동선/탐색 시간/카메라 체감을 오너가 테스트하고 조정하는 편이 안전하다.
