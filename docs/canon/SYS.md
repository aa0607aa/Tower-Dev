# SYS — 메타 규칙

세계 안의 사실이 아니라 **이 게임을 만드는 방식**에 대한 규칙. AI 개입 경계, 결정성, 정보 비대칭,
데이터 정책. 어겼을 때 세계관이 아니라 **프로젝트가 망가지는** 항목들이다.

---

### SYS-001 · 게임 엔진이 진실의 단일 출처(SSOT)

- **상태**: CANON
- **출처**: 설정서 v1.1 §25.4(AI 권한 경계) · 개발 가이드 §4 · COLLABORATION_PROTOCOL §1
- **내용**: 게임 엔진이 진실의 단일 출처다. **AI가 출력한 텍스트만으로** HP·아이템·위치·NPC 생존·
  역사 결과·계단 귀속·열매 효과를 바꾸지 않는다.
- **판단**: 설정서 §25.4는 AI가 이미 확정된 맵·스탯·아이템·역사 결과·계단 귀속·열매 효과를
  임의로 바꿀 수 없다고 정한다. **"엔진이 SSOT"라는 아키텍처 표현 자체는 개발 가이드와 협업
  프로토콜에서 온 구현 원칙**이다. 설정서 단독 출처로 오해하지 않는다.
- **구현**: 전 PHASE · TEST_CHECKLIST G-5
- **관련**: SYS-002, SYS-006

### SYS-002 · AI는 GameState를 직접 수정하지 않는다

- **상태**: CANON
- **출처**: 개발 가이드 §10 · COLLABORATION_PROTOCOL §1
- **내용**: AI는 **구조화된 Action Proposal**만 반환하고, 엔진이 검증한 뒤에 실행한다.
  거부해야 하는 것: 존재하지 않는 ID, 죽은 NPC 부활, 임의 아이템 생성, 맵·역사·계단 변경.
- **판단**: 설정서 §25.4의 AI 권한 제한을 실제 코드 경계로 구현한 **프로젝트 Hard Rule**이다.
  `Action Proposal + Validator`라는 구체 구조는 설정서 원문이 아니라 개발 가이드에서 왔다.
- **구현**: `scripts/ai/` + Validator · PHASE 9 · TEST_CHECKLIST G-5
- **관련**: SYS-001, SYS-006

### SYS-003 · 모든 랜덤은 시드 또는 결과를 저장한다

- **상태**: CANON
- **출처**: 개발 가이드 §4 · §13
- **내용**: 모든 랜덤 생성은 시드 또는 생성 결과를 저장해 **재로드 시 동일하게 복원**된다.
  플레이어가 보지 않았다고 해서 다시 생성되지 않는다.
  전역 `randi()`를 게임 로직에 쓰지 않는다.
- **판단**: 설정서의 회차/월드 선결정 데이터와 동적 상태를 재현 가능하게 만드는 개발 불변식이다.
  **전역 `randi()` 금지와 seed/result 저장 방식은 설정서 원문 문장이 아니라 구현 규칙**이다.
- **구현**: `RandomNumberGenerator` + 시드 보관 · TEST_CHECKLIST G-4
- **관련**: FLR-002, SYS-007, SYS-009

### SYS-004 · 시각 오브젝트와 데이터 객체를 분리한다

- **상태**: CANON
- **출처**: 개발 가이드 §4
- **내용**: 스프라이트가 화면에서 사라져도 **데이터가 삭제된 것이 아니다.**
  노드는 데이터를 소유하지 않고 표시만 한다. 또한 한 시스템이 다른 시스템의 내부 데이터를 직접
  수정하지 않고 이벤트·서비스 계층을 거친다.
- **판단**: 세계관 규칙이 아니라 저장·시뮬레이션 상태와 화면 표현을 분리하기 위한 **아키텍처 Hard Rule**이다.
- **구현**: 전 PHASE · `docs/CODING_STYLE.md` §3
- **관련**: SYS-001

### SYS-007 · AI가 꺼져도 게임은 동작한다

### SYS-009 · 데이터 마이닝 대응 정책 — Tier 1·2

- **상태**: CANON
- **출처**: 오너 승인(2026-08-17) · DECISIONS `D-012` · `docs/DATAMINING_POLICY.md`
- **내용**: 데이터 마이닝을 **차단하려 하지 않는다.** 대신 **비밀을 배포 파일에 담지 않는 방식**으로
  설계한다. 아래 두 층은 확정된 규칙이다.

  **Tier 1 — 정답을 배포하지 않고 생성기를 배포한다**
  - 생성 결과는 배포 파일이 아니라 **세이브에 산다** (`SYS-003`)
  - 월드·회차 단위 귀속을 유지한다 (`ITM-002` 열매, `SKL-004` 유니크)
  - **파일에 "정답 테이블"을 만들지 않는다.** 예: `열매 → 효과` 매핑을 배포 데이터로 두지 않는다
  - 미발견 정보를 UI·AI 컨텍스트에 넣지 않는다 (`SYS-005`)

  **Tier 2 — 진짜와 가짜를 구별할 수 있는 흔적을 남기지 않는다**
  - **`is_dummy` 같은 플래그를 절대 만들지 않는다.** 어떤 이름으로도
  - **더미 전용 파일·폴더·ID 대역을 만들지 않는다**
  - 모든 데이터는 종류에 관계없이 **동일한 검증 규칙을 통과해야 한다** (`FLR-011`의
    `clues[]` 필수 포함). 진짜에만 적용되는 규칙은 곧 "진짜 판별기"가 된다
  - 개발용 구분이 필요하면 **배포에 포함되지 않는 외부 매니페스트**로만 관리한다

  **Tier 3(실제 볼륨·더미 콘텐츠 투입)은 BACKLOG다** — `docs/BACKLOG.md` B-001.
  콘텐츠 제작 단계에서 다시 판단한다. 지금 데이터 포맷에 예비 필드를 넣지 않는다.
- **구현**: PHASE 2 `data/floors/floor1_fixed/` 포맷부터 적용 · 전 데이터 스키마의 검증 규칙
- **관련**: SYS-003, SYS-005, SYS-014, FLR-001, FLR-011, ITM-002

### SYS-014 · 1층 지형은 은닉 불가능하며, 그 전제로 설계한다

- **상태**: CANON
- **출처**: 오너 승인(2026-08-17) · DECISIONS `D-012` Q3 · 오너 재확인(2026-08-18)
- **내용**: `FLR-001`(1층 고정 지형)의 필연적 결과로 **1층의 초기 맵과 고정 위험 구조는 배포 데이터에서
  원리적으로 은닉할 수 없다.** 더미 맵을 섞어도 실제로 로드되는 고정 정의는 추적할 수 있다는 전제로 설계한다.

  | 1층에서 숨길 수 있다 (동적 결과) | 숨길 수 없다 (고정 정의) |
  | --- | --- |
  | 어느 파밍 지점에 무엇이 있는가 / 이미 루팅됐는가 | 방·통로·막다른 길의 초기 배치 |
  | 어떤 유배자가 어디 스폰되는가 | 함정의 **위치·종류·구조와 고정 단서** |
  | 함정의 활성·소모(`armed/fired`) 상태 | 고정 파밍/스폰 지점의 존재와 초기 지형 |
  | 파티별로 층 진입 시 실체화된 실제 계단 위치 | — |

  **따라서 1층 튜토리얼은 "고정 맵과 고정 함정 구조가 공개된 상태"를 전제로 설계한다.**
  이는 손실이 아니라 의도에 부합한다 — `FLR-015`는 지형·위험지점 암기 자체를 영구 성장으로 규정한다.
  계단은 고정 후보표가 아니라 파티/층 진입 상태에서 별도로 실체화되는 특수 시설이므로
  **고정 1층 지형의 일부로 취급하지 않는다.**
- **판단**: 이전 표의 "함정 종류는 시드로 숨김"과 "계단 후보 지점은 고정"은 설정서 §6.1보다
  범위를 넓힌 해석이었다. 2026-08-18 오너가 **함정 종류/위치는 고정, 상태만 변동**이라고 재확인하고,
  계단은 층 진입 시 별도 계산하는 방향을 제시했으므로 정정한다.
- **구현**: PHASE 2~3 함정·계단 설계 전반
- **관련**: FLR-001, FLR-002, FLR-015, CHR-014, SYS-009

  문구의 글자·띄어쓰기·기호는 고정하며 다른 문구로 랜덤 변형하지 않는다.

  출력하는 일반 층 메시지로 확대하지 않는다. 표시 위치·애니메이션·지속시간·효과음은 DESIGN이다.
- **구현**: RunState 시작 이벤트 → 공통 시스템 알림 UI · 구현 PHASE는 UI 통합 시점에 배치
- **관련**: `D-018`, WLD-004

### SYS-016 · 랜덤 인카운터는 저작된 골격 위에서 세부만 랜덤화한다

- **상태**: CANON
- **출처**: 소설 초반 원문 캡처 · DECISIONS `D-024`
- **내용**: 랜덤 인카운터는 모든 내용을 즉석에서 무작위로 만드는 방식이 아니다.
  먼저 **저작된 시나리오 골격(EncounterTemplate)** 이 존재하고, 그 인카운터가 출현할지 여부와
  허용된 세부 슬롯·인물/세력/배치·소규모 변수만 랜덤으로 정한다.
  템플릿이 가진 핵심 사건 비트, 성립 조건, 클리어 논리는 임의 랜덤으로 붕괴시키지 않는다.
- **판단**: 로그라이크의 랜덤성은 유지하되 원작의 "기본 토대가 되는 시나리오를 따르고 사소한 부분은 랜덤"이라는 구조를 따른다.
  `KGD-004`의 팩션전은 이 일반 규칙의 구체 사례다.
- **구현**: `EncounterTemplate → eligibility/appearance roll → fixed beats → randomized slots → resolved result save` 계열.
  생성 결과는 `SYS-003`에 따라 저장한다.
- **관련**: KGD-004, SYS-003, HIS-002
