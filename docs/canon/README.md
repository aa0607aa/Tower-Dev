# docs/canon/ — Canon 색인 체계

> **이 폴더는 canon이 아니다. canon의 색인이다.**
> 진실의 원본은 `docs/SETTING_BIBLE_v1.1.docx`이고, 후속 확정 결정은 루트 `DECISIONS.md`다.
> 이 폴더와 원본/후속 결정이 다르면 우선순위에 따라 **색인을 고친다.** 색인을 고쳐 canon을 만들 수 없다.

## 왜 만들었나

설정서는 사람이 읽는 산문이고 실제 개발 질문은 "1층 서든데스가 몇 초인가", "계단 관련 TBD가 무엇인가",
"이 코드가 어떤 설정을 깨뜨리는가"처럼 낱개 사실 단위다. 여러 AI가 기억을 공유하지 않는 프로젝트에서
매번 전체 설정서를 다시 읽으면 비용과 오해가 커지므로, canon을 **ID가 있는 작은 항목**으로 분해해 도메인별로 묶는다.

## 현재 구조 — 15도메인

초기 색인의 "예약 도메인(아직 파일 없음)" 설명은 폐기됐다. 현재 위 15개 도메인이 모두 실제 파일로 존재한다.
항목 수와 최신 상태는 항상 `INDEX.md`를 기준으로 본다.

## 항목 ID

형식은 `<도메인>-<번호>` — 예: `FLR-004`, `CHR-001`.

- **번호는 재사용하지 않는다.** 항목을 다른 곳으로 통합해도 기존 ID는 포인터/Retired 흔적으로 남긴다.
- 코드 주석에서 설정 근거를 밝힐 때 ID를 쓴다.
- `D-0XX`는 "언제 무엇을 결정했나"라는 **결정 이력**, `FLR-0XX` 등은 "지금 무엇이 참인가"라는 **상태 색인**이다.
- 같은 사실을 여러 도메인에서 독립적으로 유지하지 않는다. 한 곳을 정본으로 두고 다른 곳은 `관련`/포인터로 참조한다.

## 항목 형식

```markdown
### DOM-000 · 한 줄 제목

- **상태**: CANON
- **출처**: 설정서 v1.1 §0.0 · DECISIONS D-000
- **내용**: 한 항목에 한 사실만 적는다.
- **판단**: 원문 그대로가 아닌 분류/해석/구현 제약의 근거. 판단이 없으면 생략.
- **구현**: `data/...` · PHASE N
- **관련**: DOM-001, OTH-002
```

`DOM-000`은 실재하지 않는 예시 ID다.

| 필드 | 규칙 |
| --- | --- |
| **상태** | `CANON` / `DESIGN` / `TBD` / `PROPOSAL`, 필요하면 `CANON / TBD` 혼합 |
| **출처** | 어디서 왔는지. 출처 없는 항목은 만들지 않는다 |
| **내용** | 한 항목에 한 사실. 같은 사실의 정본을 두 군데 만들지 않는다 |
| **판단** | 원문을 그대로 옮긴 게 아닌 부분의 이유. 판단이 없었으면 만들지 않는다 |
| **구현** | 닿는 코드·데이터·PHASE. 없으면 `-` |
| **관련** | 함께 봐야 할 항목/정본 포인터 |

### 판단 필드를 언제 쓰나

**출처**는 "어디서 왔나", **판단**은 "왜 이렇게 적었나"다.

판단을 기록하는 경우:

- 상태(CANON/DESIGN/TBD)를 고르는 데 해석이 들어간 경우
- 설정서에 없는 오너 결정/개발 가이드 Hard Rule을 적용한 경우
- 도메인 배치나 정본 위치가 자명하지 않은 경우
- 순진한 구현이 canon을 깨기 쉬워 구현 제약을 설명해야 하는 경우
- 원문을 요약하면 오해가 생기기 쉬운 경우

**판단을 기록하지 않는 경우**: 원문을 그대로 옮긴 항목. 판단이 없었는데 전 항목에 억지로 backfill하면
다음 AI에게 존재하지 않았던 논리를 만들어 전달하게 된다.

설정서 §26의 순수 TBD도 "원문이 TBD라서 TBD"라는 당연한 문장을 반복하지 않는다. 단, `RAC-004`처럼
**일부 사실은 확정이고 상세만 TBD**인 경우에는 왜 혼합 상태인지 판단을 적는다.

## 상태

| 상태 | 의미 | 바꿀 수 있나 |
| --- | --- | --- |
| `CANON` | 확정된 세계·규칙/후속 Hard Rule | 오너 승인 없이 의미 변경 금지 |
| `DESIGN` | 채택한 구현·밸런스 구조 | 테스트로 튜닝 가능, 구조 변경은 승인 필요 |
| `TBD` | 의도적 미정 | **임의 확정 금지** |
| `PROPOSAL` | 미승인 제안 | 오너 승인 전에는 적용 금지 |

`TBD`도 반드시 색인에 남긴다. 빈칸을 다음 AI가 합리적인 기본값으로 지어내는 것을 막기 위해서다.

## 규칙

1. **여기서 canon을 만들지 않는다.** 원본/DECISIONS에 없는 내용은 `[CANON CONFLICT]` 또는 Proposal로 올린다.
2. 원본과 어긋나면 색인을 고친다. 원본을 조용히 바꾸지 않는다.
3. **한 항목에 한 사실, 한 사실에 한 정본.** 다른 도메인에서 필요하면 참조한다.
4. TBD를 구현 편의로 채우지 않는다.
5. 항목 상태/제목/정본 위치를 고치면 `INDEX.md`도 같은 작업에서 고친다.
6. 설정서 밖에서 추가된 유효 규칙은 `INDEX.md`의 **「설정서 정본 외에서 추가된 유효 규칙」** 표에도 기록한다.
7. 문서 수정 시 파일 끝 LF를 유지한다.

## 왜 별도 JSON 색인을 두지 않았나

Markdown 본문과 JSON을 둘 다 사람이 유지하면 반드시 어긋난다. `INDEX.md`의 고정된 표와 grep으로
필요한 기계 검색을 처리하고, canon 상태의 단일 색인을 유지한다.

```text
grep -rn "TBD" docs/canon/
grep -rn "FAC-" docs/canon/
grep -rn "FLR-004" . --include=*.gd
```

### 감사에서 확정한 유지 원칙

- 커버리지 감사만으로는 충분하지 않다. **없는 내용을 넣었는지/있는 내용을 빠뜨렸는지** 제3자 역대조가 필요하다.
- 관련 사실이 여러 도메인에 언급되는 것은 가능하지만 **같은 사실을 두 곳에서 독립 유지하지 않는다.**
- CANON 본문은 원문 사실, `판단`은 그 사실에서 도출한 구현/분류 이유를 구분한다.
- DESIGN/TBD라는 이유만으로 판단 필드를 자동 생성하지 않는다.
- ID 중복은 기계 검사할 수 있지만 **내용 중복은 사람이 의미 단위로 확인**해야 한다.

### 과거 ID 재배정 기록

흔적은 FAC.md 하단에 보존한다. **이후 ID는 재사용하지 않는다.**
